# Research Brief → DEC-024: HTML dashboard render target

**Type:** template-maintenance decision · record in **root `decisions/decision-024-*.md`** (not `.claude/support/decisions/`). **Status:** ready for `/research`. **Substrate/evidence:** this directory (`/.claude/support/workspace/dashboard-html-exploration/`).

## Problem

The template's project dashboard (`.claude/dashboard.md`, generated by `.claude/scripts/dashboard-render.py` — the Family-C script, 54 tests) is Markdown. At scale it breaks down as a *read* surface (styler: 640 lines / 28,232 px tall; a 141-row decision "table hell"; 53 repeated phase headers), and the user reports rarely reading the raw Markdown at all. A multi-iteration prototype (this dir) validated a replacement direction with the user.

## What's SETTLED (do not re-litigate in research — user-validated via prototype)

- The human dashboard becomes a **single, read-only, visualization-forward HTML page**, generated from the same source data (task JSON + sidecar) the Markdown is today. User reads it for overview; acts via CLI. ("I wouldn't even need the Markdown once I have this.")
- **Content is curated, not dumped:** pulse (completion ring + status donut + counts), a 53-phase **heatmap**, active-front cards, a "Needs you" panel, Recent-with-descriptions; **decisions collapsed → searchable on open**; an adaptive **dependency/critical-path graph + timeline** (shown only when meaningful); and a collapsible **Specification browser** (the spec's `##` sections, rendered to HTML on expand, filterable).
- **State of record stays in task JSON** (Claude reads that, not the dashboard). **Drift detection is unaffected** (it hashes the spec, not the dashboard).
- Curated HTML is *lighter* than today's Markdown when content isn't embedded (23 KB vs 64 KB for styler's overview).

## OPEN sub-decisions — the actual research targets

1. **Asset-loading & the `file://` constraint (the crux).** How does the user open it? `file://` blocks `fetch()`/CORS and can restrict CDN scripts — so *lazy-loading* spec/decision sections from sibling files won't work under `file://`. Options: **(a) embed everything** (works offline + `file://`, but styler's file → ~1 MB); **(b) lazy-load, require a local server** (`python3 -m http.server`, friction); **(c) hybrid** — embed lightweight section *headings/index*, lazy-render embedded raw text on expand (current prototype: ~1 MB but instant + offline); **(d)** ship a tiny `dashboard serve` helper. Resolve this first — it gates 2, 3, 6.
2. **Markdown→HTML rendering.** Bundle `marked.js` (CDN → breaks offline) vs **vendor/bundle it locally** vs **server-side render in Python** (stdlib has no markdown lib → vendor one, or hand-roll) vs minimal hand-rolled inline converter.
3. **Mermaid dependency graph.** Bundle `mermaid.js` vs **pre-render SVG in Python** (no runtime dep; also fixes the live FB-007 broken-mermaid bug seen in OEMMatInsightBI) vs drop the graph (user deprioritized it).
4. **Tracked vs gitignored.** A generated view argues for gitignore + regenerate-on-demand; but a tracked artifact gives history/blame. (If embedded-and-large, gitignore avoids repo bloat + the 108K-char-line diff problem.)
5. **Freshness / machine-read.** `/work` Step 1a reads `task_hash` from the dashboard META to decide regen. Where does it live now — a small HTML `<!-- META -->`/`<script type=application/json>` header block, or move freshness to the sidecar?
6. **`dashboard.md` disposition.** Full retire vs keep a minimal MD fallback for the "no `python3`" path (the current prose fallback in `dashboard-regeneration.md` assumes MD).
7. **Render pipeline.** Extend `dashboard-render.py` to emit HTML (reuse its data layer — the prototype's `viz.py` regex-scrapes the *rendered MD*, which the real one must NOT do; read task JSON directly) vs a new emitter. What happens to its 54 tests + the LLM-filled synthesis sections (Action Required, Custom Views)?
8. **Scale-gating & adaptivity.** Which sections/viz render at which project sizes; auto-hide degenerate graphs (near-done projects); the small-project case (renovation/12-task) must still look right.
9. **Migration.** 11 existing downstream dashboards. One-shot regen on next `/work`? Format-staleness already triggers regen via `template_version`.

## Constraints / invariants it touches (enumerate impact in the DEC)

- Preserves the **single `spec_v{N}.md`** invariant (untouched). Drift/`fingerprint.py` unaffected (hashes spec).
- `rules/dashboard.md` + `support/reference/dashboard-regeneration.md` → substantial rewrite. `.claude/CLAUDE.md` Navigation + Critical Invariants. `settings.json` `permissions.ask` (no longer guarding `dashboard.md` edits if it's generated).
- The marker/sidecar system (`dashboard-state.json`) — user notes/toggles move fully into the sidecar (user no longer hand-edits the view). Confirm this is clean given the user doesn't edit the dashboard.
- `disable-model-invocation` / agent read-paths that currently parse `dashboard.md`.

## Recommended lean (for the research-agent to pressure-test, not adopt)

Single HTML, **option 1(c) hybrid** (offline + `file://`-safe, no server friction), **Python-side rendering** for md→HTML and **pre-rendered SVG** for the graph (zero runtime CDN deps → fully offline, fixes FB-007), **gitignored + regenerated** by an extended `dashboard-render.py` reading task JSON directly, with a **minimal MD fallback** retained for the no-`python3` path. Lazy-load (1b) is the main rival if file sizes prove painful and a served dashboard is acceptable.
